# Design Notes — cad_dataset_generator

Живой журнал решений. Изменения фиксируются по мере реализации; таблицы с
измерениями служат базой для ручной корректировки весов в `config.py`.

## Цели проекта (приоритеты)
1. Корректность: `программа ↔ геометрия ↔ (point cloud/render)` обязаны
   совпадать — параметры фиксируются в узле ТОЛЬКО после успешного execute+validate.
2. Воспроизводимость: один seed → одна программа и геометрия (det-логика через
   `np.random.default_rng`, отказа нет).
3. Разнообразие: не допускать вырождения к «box+extrude»; распределение операций
   управляется весами в конфиге.
4. Контролируемая сложность: easy/medium/hard/expert по числу операций + бюджет.
5. Скорость: minimиза attempts/retry через валидные по построению параметры.

## Архитектура (упрощённо)

```
Program Sampler (ASTBuilder, бюджет/лимиты/веса)
   → Parameter Generator (параметры, валидные по построению, см. таблицу ниже)
   → Geometric Preconditions (фильтры: bbox, простота ребёнка, лимиты)
   → CadQuery Executor (node_id → cq.Shape, мемоизация)
   → Geometry Validator (BRepCheck/объём/bbox; root→ShapeFix)
   → COMMIT (запись операции + каунт) / ROLLBACK (_save_state/_restore_state)
```

Генерация **transactional**: узел добавляется в AST и учитывается в `total_ops`
только после успешного `execute` + `validate`. Неудача кандидата откатывает RNG
и счётчики (`_restore_state`), поддерево ребёнка при этом остаётся в executor-кеше
и переиспользуется следующими кандидатами.

## Диагноз медленной генерации (март 2026)
Измерено на 25/60 medium-деревьях и 200-свипе:
- финальных операций ~592 → `executor.execute` ~4898 (≈8.3×), не из-за повторного
  исполнения поддерева (кеш по node_id есть), а из-за **отброшенных поддеревьев**
  при неудачных попытках и **повторных сборок на `_reset`**.
- Доля неудач кандидатов до фикса (25 medium): fillet **71%**, chamfer **71%**,
  split **24%**, boolean **17%**, hole 0%, shell 0%.
- Основные потребители времени по профилю (exec-тайминги, %):
  - easy:   rarray 20-42%, cut 9-20%, union 9-17%, hole 4-7%, split 3-21%
  - medium: split 29-49%, validate 15-17%, union 9-16%, rarray 6-17%, cut 5-11%
  - hard:   split 25-46%, validate 14-20%, polarArray/union/cut по ~4-5%
- Вывод: узкое место — **не отдельные операции** (boolean ~0.005s, fillet ~0.005s,
  shell ~0.002s, rarray 3×3 ~0.023s), а **серии неудачных попыток**, каждая из
  которых пересобирает поддерево с новыми node_id. `sample_timeout=150`/`60 attempts`
  — это следствие, а не причина.

## Параметрическая модель «валиден по построению» (по каждому вызову API)

Каждый вызов реализуется так, чтобы первые же сгенерированные параметры были
геометрически валидны; retry-петли сведены к редкой страховке.

| Вызов (операция) | Что делает в OCCT/Cq | Генерация параметров (валидна по построению) | Страховка |
|---|---|---|---|
| `box/cylinder/sphere/cone/wedge/torus` | прямое построение примитива | диапазоны >0; torus: `r2 <= 0.7*r1`, `r2>=0.2` | валидатор |
| `extrude/revolve/twist_extrude` | лофт/solid из эскиза | эскизы «закрытые однократные провода» (polyline/spline через convex hull), twist angle 5..60° | валидатор |
| `loft` | профили на разных высотах | 2-3 профиля одного семейства, центры (0,0), offsets строго возрастающие | валидатор |
| `sweep` | профиль по пути | профиль=circle (надёжный), путь=spline/polyline по возрастающему X | валидатор |
| `fillet` | скругление выбранных рёбер | **радиус из фактической длины выбранных рёбер**: `r ∈ [0.02, min(0.3×min_len, 0.1×min_dim)]` | 1 попытка |
| `chamfer` | фаска рёбер | **аналогично fillet**: `d ∈ [0.02, min(0.3×min_len, 0.1×min_dim)]` | 1 попытка |
| `shell` | полость тела с удалением грани | только ребёнок «простой» (без boolean/pattern/shell/loft/sweep/hole); `t = 0.5–1×min_dim×0.02`; 6 направлений | объём < 0.995×base |
| `hole` (through/blind/cbore/csk) | вырез цилиндра/конуса | position внутри bbox с запасом ≥radius; r ≤ 0.4×min(w,h), r_max≥0.1; через всё тело depth=+запас | объём < 0.995×base |
| `split` | разрез плоскостью через центр + fuse половин | **ось по max-экстенту**, `gap ∈ [0.25,0.4]×extent` (перекрытие половин → единый Solid), 1 gap на ось | 1 попытка/ось |
| `translate/rotate/mirror` | аффинные преобразования | диапазоны ±15/углы 15–345°, плоскости XY/XZ/YZ | не валидируем (гарантия) |
| `rarray` | серия fuse копий | nx,ny∈[2,4], **nx×ny ≤ 6** (было до 16 — секунда на операцию), spacing ∈ [0.4,0.9]×min_dim (перекрытие) | валидатор |
| `polarArray` | круговая раскладка+фуза | count 3-4, radius ∈ [0.2,0.45]×min_dim, fill=True | валидатор |
| `scatter` | точки + fuse | 2-4 точки в круге r ≤ 0.45×min_dim | валидатор |
| `union/cut/intersect` | булева математика BRepAlgoAPI | **bbox-прегейты до исполнения**: перекрытие ≥2% объёма, union — правый не внутри, cut/intersect — инструмент не накрывает тело целиком; offset из центров + jitter | объёмные чеки после |

## Вероятности выбора операций (текущие, после ребаланса)

Фиксированы в `config.py`. Правило: «попробовать модификатор» — с пост-W-вероятностью;
порядок унарных/бинарных/листовых — через `_weighted_order` (вес выше → чаще первым).

**`modifier_probabilities`** (вероятность «попробовать» кандидата):
| op | p | примечание |
|---|---|---|
| translate/rotate/mirror | 1.0 | дешёвые и гарантированные |
| shell | 0.3 | дорогой, только простые тела (повышено с 0.12 для сохранения доли) |
| fillet/chamfer | 0.6 | теперь от длины ребра — дешёвые |
| rarray/polarArray/scatter | 0.6 | только простые тела |
| hole | 0.5 | |
| split | 0.6 | дорогой (plane-cut+fuse); снижен с 1.0 |

**`unary_choice_weights`**: fillet 5, chamfer 5, hole 5, split 3.5, arrays 3,
transforms 2.5, shell 3.5 (повышено с 2.0 — выше было недостижимо из-за
short-circuit в `_weighted_order`).
**`binary_choice_weights`**: union 5, cut 5, intersect 2.
**`leaf_choice_weights`**: примитивы 1.0, extrude/revolve/twist 1.2, loft/sweep 2.5
(поднимаем редкостные).

Целевые доли реализованных операций (по 60 medium-деревьям до/после):
- было: transforms 38%, split 8.3% (в 81% деревьев), shell/rarray/polyline — единичные;
- цель: transforms+mirror ~20%, split ~4-6%, shell/loft/sweep/arrays заметно выше.

## Задометры (backstops), которые остаются как редкая страховка
- `sample_timeout=150` + принудительный перезапуск воркера — ловит только
  настоящий OCCT-hang внутри одной операции (wall-cap между операциями не видит).
- wall-clock кап в `build()`: `attempt_timeout×4` (easy 8s, medium 15s, hard 20s, expert 30s).
- `backtrack_attempts=60`, `max_seed_retries=50`.
- Воркер-кап пула = 8 (Windows spawn WinError 87 при массовом создании процессов).

После фиксов эти механизмы не должны быть основной потерей времени; если сэмпл
падает с «Failed after N attempts», это сигнал к корректировке параметрической
модели, а НЕ к увеличению ретраев.

## Известные ограничения / открытые вопросы
- Воспроизводимость: `fast_bbox` (`_fromTopoDS(optimal=False)`) на холодном кеше
  OCCT может отличаться в последних битах мантиссы, и эти значения питают границы
  `rng.uniform` в `_try_hole`/`_try_split`. **Фикс (авг 2026)**: bbox-значения в
  билдере квантуются до нанометров (`_bbox`/`_min_dim`/`_center`), прогнаны
  10×10 парных сборок одного seed — 0 расхождений. Триангуляция остаётся только
  для эвристик/метрик, не для метаданных.
- Валидация каждого узла (BRepCheck+объём+bbox) ≈ 14-20% времени в hard —
  кандидат на «лёгкую» валидацию внутренних узлов (полный анализ только на root).
- hard/expert могут содержать отдельные OCCT-hang при сложных комбинациях
  (split/fuse на body после pattern/shell) — это лечится предгейтами (простота
  ребёнка), а не ретраями.
- План на 50k: все четыре сложности поровну; после фиксов оценка ~5 часов на
  8 воркерах в режиме `--programs-only`.

## Выходной формат датасета и рендер (авг 2026)

**Решение (п.2):** по умолчанию генератор пишет ТОЛЬКО исполняемые программы,
разбитые по папкам сложности, чтобы сгенерировать корпус один раз и варьировать
сложность на этапе обучения выбором подпапки:

```
output/
  easy/    sample_00000.py, sample_00004.py, ...
  medium/  sample_00001.py, sample_00005.py, ...
  hard/    sample_00002.py, ...
  expert/  sample_00003.py, ...
```

- Сложность по-прежнему назначается по кругу `complexity_levels[index % 4]`,
  поэтому каждый батч из 4 сэмплов равномерно покрывает все уровни.
- Дополнительные форматы (step/stl/pointcloud/mesh/render/ast_json/metadata_json/
  program_txt) включаются флагом `--export-formats step,stl,...`. В этом режиме
  каждый сэмпл получает подпапку внутри своей сложности:
  `output/{complexity}/sample_NNNNN/` с `program.py`, `metadata.json`, `ast.json`
  и запрошенными экспортами. `metadata.json`/`ast.json` пишутся всегда в полном
  режиме (дёшевы и нужны для обучения).
- `--flat` отключает разбиение по сложности (плоский вывод в `output/`).
- `config.py`: `save_formats` по умолчанию `["program_py"]`,
  `split_by_complexity=True`; поле `flat_py_only` удалено (заменено
  `split_by_complexity`).

**Рендер.** Старый `RenderExporter` ставил камеру в origin с identity-pose и не
наводил её на модель: для моделей, центрированных у начала координат, камера
оказывалась внутри/вплотную к телу, и кадр получался пустой/белый. **Решение:**
исправить, а не выпиливать — камера теперь кадрирует bbox модели (look-at на
центр, дистанция ~3× max-extent, свет из направления камеры). Ограничение
окружения (headless без OpenGL/EGL) остаётся: рендер — единственный формат,
зависящий от графического контекста; в таких средах его просто не запрашивают
(без `--export-formats render` он не используется).

## Узкое место генерации и план A1+A2+B4+B5 (авг 2026)

Профиль (20 easy / 20 medium / 15 hard / 6 expert):
- hard: avg **6.7s**, max **36.7s**, p90 11s; dispatch 167.8 при 17.6 финальных
  ops — **9.5×** «лишней» работы;
- expert: 3.3–106s; seed2 — **106s** (1211 rollback, **4688 dispatch**); seed3 —
  **fail после 318s** (wall-cap не сработал внутри одной OCCT-операции).

Причина — не отдельные операции, а **лавина retry**:
1. `_try_binary_ops` в «сбалансированном» режиме строил ДВА больших операнда и при
   «оба сложные» возвращал None — оба поддерева (~10–30 ops) строились и
   исполнялись впустую, затем на откате строилось ещё одно.
2. Внутренние retry-циклы на не-простых телах: hole до 8 кандидатов × N серий
   попыток, boolean 5 jitter, shell до 8, split до 3 осей — на каждом из ~30
   узлов дерева (seed7/hard: 561 dispatch, 123 rollback, но всего 12 реальных
   валидационных отказов).
3. Полная валидация каждого (в т.ч. отброшенного) кандидата: ~2.3s/сэмпл для
   hard (Volume + Solids + bbox по сетке).
4. Таймауты-ожидания: единый `sample_timeout=150s` (easy живёт ~32s — пул ждёт
   зависший воркер в 4–5 раз дольше нужного; grace ещё +150s); wall-cap
   `attempt_timeout×4` НЕ проверяется внутри длинной OCCT-операции (expert seed3 —
   318s); `deadline_hits>=10` позволяет 10 раз пересобрать всю попытку.

**Решение (A1+A2+B4+B5)** — разнообразие программ не урезается:
- **A1** — булевы без «слепых» поддеревьев: сначала строится только первый
  операнд; первый получает либо почти весь бюджет (50% попыток), либо половину
  (50%); если он сложный/большой — второй строится как `_build_simple_feature`
  (лист только из примитивов/extrude/revolve/twist — НЕ loft/sweep — плюс цепочка
  гарантированно-простых модификаторов fillet/chamfer/split/transforms); если
  первый простой и маленький — второй получает остаток бюджета. Семейства «двух
  средних операндов» и «фича ∪ сложное тело» сохраняются; богатство фичи
  (модификаторы на втором операнде) восстановлено, поэтому hole/fillet/split не
  выпадают. Выпадает только патологическое «сложное ∪ сложное» (булевы `'11'`),
  которых и раньше не было в выдаче; гейт `not (left_simple or right_simple)`
  оставлен как страховка.
- **A2** — урезание retry-циклов: hole 8→3, boolean jitter 5→3, shell 8→4,
  leaf-попытки 4→2. Операции остаются в словаре; «валидные по построению»
  параметры дают успех обычно на 1–2 кандидате, поэтому частотность не страдает.
- **B4** — лёгкая валидация внутренних узлов: unwrap + single-solid + volume;
  bbox/диагональ и BRepCheck+ShapeFix — только для root.
- **B5** — сложность-зависимые `sample_timeout` (easy 40 / medium 75 / hard 100 /
  expert 150s), grace по максимуму таймаута оставшихся воркеров,
  `deadline_hits` 10→3 (быстрый отказ сэмпла вместо долгих пересборок).

**Измерения «до/после» (после реализации):**

Скорость на «плохих» сидах (одна сборка, s):
- hard seed7: baseline ~35s → **16.5s**; hard seed8: **0.33s**;
- expert seed2: baseline 106s → **0.89s**; expert seed3: baseline fail/318s → **3.29s**;
- easy/medium: ~1s / ~3.5s (в пределах таймаутов).

Полный pytest: 101 passed за ~5:54 (после фикса; до — прогон не дополнял из-за
зависаний на сборке medium).

Разнообразие (25 сидов easy/medium/hard + 5–6 expert, до/после):
- патологические булевы `'11'` (оба операнда сложные) — в выдаче отсутствуют;
- состав близок к baseline: hard unary 11.56→10.48 (промежуточный вариант давал
  8.12), binary 2.56→2.56; fillet/split на фичах восстановлены (hard fillet
  0.44→0.80, split 1.08→1.60);
- структурный сдвиг — hole на сложности hard 1.60→0.52/сэмпл и часть mirror
  (0.80): фичи забирают бюджет у модификаторов тел, и hole исключён из
  «простых» фич (он входит в «сложные» операции). Семейства операций не удалены:
  hole присутствует на всех сложностях; тест `test_new_ops_diversity` (80 medium)
  и `test_profile_rebalance_keeps_groups` (60 medium) проходят.

## Вероятности операций и возобновление генерации (авг 2026)

**Трансформации translate/rotate/mirror — вероятность 0.3.**
Раньше `_should_try_unary` возвращал безусловный `True` для всех трёх
(ast_builder.py) — они встречались чаще остальных модификаторов (hard mirror
~2.76/сэмпл). Теперь `translate/rotate/mirror` добавлены в
`config.modifier_probabilities` со значением 0.3, и тот же фильтр применяется к
трансформациям в `_build_simple_feature` (второй операнд булевых не тащит
трансформации; fillet/chamfer/split там не трогаем). Следствие: при
неудачном «подбрасывании» всех унарных кандидатов унарный путь чаще откатывается
к листу — состав слегка смещается в сторону листьев (ожидаемо, согласовано).

**Порядок весов терминальных листьев — «наоборот»** (`config.leaf_choice_weights`):
1. extrude, revolve — **1.5** (самые вероятные);
2. twist_extrude, loft, sweep — **1.2** (средние);
3. box, cylinder, sphere, cone, wedge, torus — **1.0** (самые редкие, не трогаем).
Раньше было extrude/revolve/twist 1.2 и loft/sweep 2.5 (лидеры). Замечание:
loft/sweep дополнительно отсекаются «рисковым» пулом `_build_leaf_solid` (25%
попадания в пул), поэтому их фактическая частота ниже веса — механизм надёжности
не меняется, он про порядок, не про риск.

**Флаг `--start-sample` (возобновление генерации).**
`main.py` получает `--start-sample N` (по умолчанию 0), прокидывается в
`generate_dataset(num_samples, parallel, start_sample)`. Семена считаются по
**абсолютному диапазону**: `SeedSequence(global_seed).generate_state(start+N)` и
берётся срез `[start : start+N]` — инвариант `seed(i) = states[i]` не зависит от
размера чанка. Поэтому прогон 30 сэмплов за раз даёт те же программы, что и два
прогона по 15 (0..14 + 15..29) при том же `--seed`. Сложность, имена файлов
(`sample_{index:05d}*`) и таймауты уже индекс-абсолютны, поэтому флаг работает
во всех режимах вывода (только программы, плоский `--flat`, полный с экспортами).
При `start_sample=0` поведение бит-в-бит совпадает с прежним.
